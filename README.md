# Person API

Небольшой REST-сервис для управления контактами: создание, просмотр, поиск, обновление и удаление людей. Это не просто CRUD поверх таблицы: бизнес-правила находятся в домене, чтение отделено от изменения данных, а конкурентные обновления защищены версией записи.

## Быстрый запуск

Нужны Docker и Docker Compose.

```bash
cp .env.example .env
docker compose up -d --build
```

Compose поднимет PostgreSQL, применит миграции и запустит API. После старта проверьте:

```bash
curl http://localhost:8080/health/ready
```

Остановка:

```bash
docker compose down
```

Данные PostgreSQL сохраняются в Docker volume. Чтобы удалить и контейнеры, и локальные данные БД, выполните `docker compose down -v`.

## API

- `POST /person` — создать запись.
- `GET /person/{id}` — получить запись.
- `GET /person?limit=20&offset=0&search=anna` — список с поиском и пагинацией.
- `PUT /person/{id}` — изменить запись; в теле обязателен `version`.
- `DELETE /person/{id}` — удалить запись; в теле обязателен `version`.
- `GET /health/live` и `GET /health/ready` — проверки состояния сервиса.

Пример создания:

```bash
curl -X POST http://localhost:8080/person \
  -H 'Content-Type: application/json' \
  -d '{"email":"anna@example.com","phone":"+79991234567","firstName":"Анна","lastName":"Иванова"}'
```

В ответе на создание сервис вернёт `id` и `uri`. Получить текущую версию записи можно через `GET /person/{id}`. Её нужно передавать в `version` при обновлении или удалении. Подробные ошибки возвращаются в едином формате с кодом ошибки и `requestId`.

## Что здесь интересного

- **Clean Architecture.** HTTP, сценарии приложения, доменная модель и PostgreSQL разделены. Бизнес-правила не зависят от веб-фреймворка или конкретной БД.
- **DDD в разумном масштабе.** `Person` — доменный агрегат: он нормализует и проверяет данные, а наружу не отдаёт поля для произвольного изменения.
- **CQS и CQRS.** Команды изменяют состояние (`Create`, `Update`, `Delete`), запросы читают (`Get`, `List`). Для чтения и изменения предусмотрены разные обработчики и порты. Это разделение на уровне кода, без лишней инфраструктуры и отдельного брокера сообщений.
- **Оптимистическая блокировка.** У каждой записи есть `version`. Изменение или удаление выполняется только при совпадении ожидаемой версии, поэтому устаревший запрос не затрёт чужие изменения молча.
- **Unit of Work и транзакции.** Работа с агрегатом и записью организована через транзакционную границу; незакоммиченная транзакция откатывается.
- **Защита на нескольких уровнях.** Валидация доменных данных дополняется ограничениями и индексами PostgreSQL. Нормализованный email уникален, а список имеет стабильный порядок и индекс для сортировки.
- **Практичная эксплуатация.** Таймауты HTTP и БД, ограничение размера тела запроса, request ID, структурированные логи, recovery middleware, health checks и graceful shutdown.

Идея простая: оставить сервис небольшим, но не превращать его в набор обработчиков, которые напрямую пишут SQL и надеются, что всё будет хорошо при параллельных запросах.

## Разработка и проверки

Нужен Go **1.27.2**. Основные команды собраны в `Makefile`:

```bash
make test          # unit-тесты
make test-race     # тесты с race detector
make test-integration # интеграционные тесты PostgreSQL
make lint          # golangci-lint закреплённой версии
make check         # полный локальный набор проверок
```

Для интеграционных тестов нужна отдельная тестовая БД; параметры подключения задаются через `TEST_DATABASE_URL`. Пример переменных окружения находится в `.env.example`.
